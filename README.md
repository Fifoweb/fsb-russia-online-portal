## Упоминания участников сервера ФСБ — 26.10.2026

«Отчёт старших» поддерживает до пяти Discord username или ID. Порядок перенесён из `Fifoweb/ysb-russia-online-wiki`: сервер проверяет webhook, определяет Discord guild, делает Bot-auth поиск `/api/v10/guilds/{guildId}/members/search?query=...&limit=1000` и выбирает точный username без учёта регистра. Для ID используется GET конкретного участника. Отображаемое имя и серверный ник не заменяют username. Адресату не нужен аккаунт на портале ФСБ.

Если хотя бы один человек не найден или имя неоднозначно, новый отчёт не сохраняется и сообщение не отправляется; форма показывает номер строки и предлагает Discord ID. Пустые строки пропускаются; если все пустые, отмечается роль старшего состава. Одинаковые имена и ID не дублируют уведомления. При вводе нет живого поиска. Кнопка «Проверить получателей» выполняет только чтение и не сохраняет отчёт; при отправке проверка выполняется заново.

Новые заявки используют `portal_save_guild_senior_report` и источник `discord-guild` в снимке получателей. SQL принимает только сервисные вызовы, проверяет FSB guild `1538689087228346450`, до пяти уникальных ID и неизменяемый профиль автора. `allowed_mentions` разрешает только автора и найденных участников либо одну выбранную роль. История прежних отчётов не переписывается. Старые UUID и формат незавершённых запросов сохраняются. Очередь, RLS, проверка Auth и защита от повторения неопределённого Discord POST остаются прежними.

Секрет `DISCORD_BOT_TOKEN` добавляется только в Supabase; бот должен находиться на Discord-сервере ФСБ. Токен не хранится в клиенте, документации или ZIP. Канал и webhook остаются ранее заданными. Source: https://github.com/Fifoweb/ysb-russia-online-wiki/blob/main/supabase/functions/submit-senior-promotion-report/index.ts .

Проверки: 10 новых тестов поиска/обработчика; всего 78 серверных тестов и 21 клиентский Auth тест; 44 SQL проверки на PGlite. В изолированном браузере с bundled Supabase SDK проверены пять строк, пустой fallback, ошибка второй строки, несколько найденных людей и потеря ответа с последующей сверкой. Реальных тестовых отчётов/пингов не отправляли. Публикация только GitHub Pages.

## Отдел в личном кабинете — 26.10.2026

Отдел хранится на сервере для каждого аккаунта. До первой заявки на внутренний перевод человек может выбрать и сохранить М, КТЦ, УКП, А, В или УОД; выбор необязателен и доступен до привязки Discord. После сохранения заявки отдел берётся из её целевого отдела. Источник показывается в кабинете как «Отдел по последней заявке». Это данные профиля по обращению, решение руководства о фактическом переводе отдельно не отслеживается.

Существующая история внутренних переводов автоматически заполнена по последней записи. Новые записи обновляют отдел атомарно с сохранением заявки в базе, независимо от доставки сообщения в Discord. Последней считается запись с максимальным created_at, затем UUID при равных временах. Повтор старой заявки и повтор доставки отдел обратно не переключают. После появления переводов устаревшая ручная форма не может перезаписать отдел; сервер возвращает действительное значение. Ручной выбор и запись перевода сериализованы блокировкой профиля.

Миграция: `20261026170919_portal_profile_departments.sql`. Отдельная таблица `portal_profile_departments` имеет RLS чтения только своего значения, служебные запись/чтение RPC вызываются через свежую авторизацию `portal-auth`. Ник, Static ID и Discord привязка не меняются. В кабинете отдел перечитывается с сервера; после подтверждённого сохранения внутреннего перевода обновляется состояние профиля.

Проверки: 4 новых endpoint теста, 9 регрессионных проверок входа, 7 проверок внутренних переводов; 23 SQL проверки начального выбора, backfill, последнего перевода, старого повтора, порядка записей, RLS и неизменяемых данных; 21 клиентская проверка Auth. В изолированном браузере с настоящим Supabase SDK проверены выбор М, сохранение после перезагрузки и обновление на А после mock заявки. Тестовых сообщений в Discord не отправляли. Публикация только на GitHub Pages.

## Отчёт старших — 26.10.2026

Новый раздел `#/applications/senior-report` находится в основном списке «Заявки». В личном кабинете сохранены карточка и собственная история отчётов. Ник, Static ID и Discord автора берутся из неизменяемого профиля и свежей identity. Поля: адресат уведомления; текущий и желаемый ранг; от 1 до 10 HTTPS-ссылок на доказательства работы (до 300 символов каждая). Ранги строго ограничены: Подполковник → Полковник → Генерал-майор → Генерал-лейтенант → Генерал-полковник; желаемое звание должно быть выше текущего. Отправление не присваивает звание.

Получатель — руководство М, КТЦ, УКП, А, В, УОД; роль «Старший состав»; либо конкретный человек по Discord username. Для роли используется один фиксированный серверный ID. Для человека приватный SQL сопоставляет точное имя пользователя с подтверждёнными Discord identities зарегистрированных пользователей портала. При единственном совпадении подставляется настоящий `<@ID>`. Если совпадения нет или оно неоднозначно, отправляется `@username` текстом; форма, результат и история явно сообщают об отсутствии уведомления человеку. Отображаемые имена не используются для выбора произвольного получателя. Свободный текст не может добавлять дополнительные упоминания.

Сервер: миграция `20261026164400_portal_senior_reports.sql`, функция `portal-senior-report`. Отдельные таблица, RLS только для владельца, атомарная очередь, стабильный UUID запроса, lease доставки и защита от повторения неопределённого POST. Общая квота отправок сохранена. Webhook и канал хранятся только в `DISCORD_SENIOR_REPORT_WEBHOOK_URL` / `DISCORD_SENIOR_REPORT_CHANNEL_ID`. Канал `1549141895496736869` проверен read-only GET; роль старшего состава `1538689087681339488`. Значение webhook не включается в клиент или ZIP.

Проверки: 8 новых серверных тестов (55 вместе с регрессиями), 75 SQL проверок на изолированном PGlite, 21 клиентская проверка Auth, ручная проверка обязательных полей, адресата, ограничения рангов, текстового ника, истории и сверки потерянного ответа. Реальные тестовые сообщения и пинги в Discord не отправлялись.


## Переводы между отделами — 26.10.2026

Добавлен раздел `#/applications/internal-transfer`: текущий отдел, желаемый отдел и причина до 1000 символов. Игровой ник и Static ID берутся из неизменяемого профиля, тег игрока — из свежей подтверждённой Discord identity. Руководство получает уведомление только для выбранного принимающего отдела: М, КТЦ, УКП, А, В или УОД. Текущий и желаемый отделы должны различаться. Отправка не меняет отдел аккаунта автоматически.

В кабинете и разделе заявок есть отдельная история внутренних переводов. Сохранение и очередь атомарны; UUID запроса сохраняется при обрыве соединения. Неопределённый исход POST не повторяется автоматически. История доступна только владельцу через RLS. Существующие восстановления и внешние переводы не изменены.

Сервер: миграция `20261026115723_portal_internal_transfers.sql`, Edge Function `portal-internal-transfer` с собственным свежим `auth.getUser` и общей квотой отправок. Секреты `DISCORD_INTERNAL_TRANSFER_WEBHOOK_URL` и `DISCORD_INTERNAL_TRANSFER_CHANNEL_ID` хранятся только в Supabase. Канал: `1553648948521209916`. Соответствия ролей фиксируются в серверной карте и закрытой таблице `private.portal_department_roles`; клиент не может выбирать произвольную роль или Discord ID. Webhook проверяет канал перед отправкой; `allowed_mentions` содержит только заявителя и одну выбранную роль.

Проверки: 7 серверных тестов нового обработчика и Discord payload; 39 SQL проверок на изолированном PGlite; существующие серверные и клиентские тесты; проверки формы, истории, ошибок и сверки запроса при потере ответа. Настоящие тестовые сообщения и пинги в Discord не отправлялись.

Вход по Static ID и паролю. Игровой ник остаётся в профиле. Доступны документы и справочник, личный кабинет, привязка Discord, заявки на восстановление и переводы в ФСБ по таблице владельца. В формах используются только игровые данные.

Публичный publishable key в браузерной конфигурации не является административным ключом.

GitHub Actions публикует только папку `dist/`. Изменения main проходят статическую проверку, поиск секретов и тесты защиты сессий и OAuth redirect. Для Pages выбран источник GitHub Actions.

Локальная проверка: `npm run check` и `npm test`; Node.js 20 или новее. Сайт открывается через HTTP, не через file://. Ссылки и OAuth поддерживают подпапку проекта на GitHub Pages.

В кабинете можно отвязать Discord с подтверждением. Вход по Static ID и паролю и история заявок сохраняются; для новых заявок требуется повторная привязка. Используется собственная сессия пользователя и штатный Supabase Auth API, серверная часть не менялась.
